# ATHENA Repo Audit (describe-only, no code changes)

## 1) Repo map
- Key packages/modules under `src/athena_mcp`: `mcp_core` (server/transports/types/bridge_client), `tools` (tool registry, schemas, ToolBank, tool wrappers), `blender_bridge` (bridge HTTP server, executor, queue/responses), plus `athena_vision_tools` package.
- Entry points / CLIs: `src/athena_mcp/mcp_core/server.py:main` (`python -m athena_mcp.mcp_core.server --http/--stdio` starts MCP server); `src/athena_mcp/blender_bridge/provider_http.py:main` (run inside Blender to expose bridge HTTP `/exec`); helper script `start_blender_bridge.ps1` in repo root for launching bridge.
- HTTP provider wiring: MCP HTTP transport in `src/athena_mcp/mcp_core/transport_http.py` mounts `/tools/list` (lists registry tools) and `/tools/call` (invokes registry `call_tool`). Bridge HTTP provider in `src/athena_mcp/blender_bridge/provider_http.py` mounts `/exec` to run Blender executor functions on the main thread.
- Tool registration: MCP tool definitions live in `src/athena_mcp/tools/registry.py` (TOOL_BANK built from ToolDefinition list; wrappers call `_call_bridge`); schemas live in `src/athena_mcp/tools/specs_v2.py` and `src/athena_mcp/tools/vision_specs.py`. Bridge tool registry is dynamic in `provider_http._build_dynamic_registry()` (auto-discovers public functions in `blender_bridge/executor.py` and applies aliases).
- Tests: under `tests/` — coverage for tool payloads/defaults (`test_add_cube_defaults.py`, `test_mesh_edit_payload.py`, etc.), transport behaviors (`test_http_server_smoke.py`, `test_stdio_transport.py`), compliance (`test_mcp_compliance.py`), registry/list/call (`test_tools_list.py`, `test_tools_call.py`), vision/tools registries (`test_vision_registry.py`, `test_athena_vision_tools.py`), bridge env/timeout (`test_bridge_request_env.py`, `test_bridge_client_timeout.py`), and tool bank/schema defaults.

## 2) Tooling flow (concrete)
- `tools/list` production: `transport_http.MCPHTTPRequestHandler.do_GET` -> `tools.list_tools()` -> returns `ToolDefinition.to_wire()` for each item in `registry.TOOLS`.
- `tools/call` validation + execution: `transport_http.MCPHTTPRequestHandler.do_POST` parses JSON, ensures `name` is str and `args` dict (also accepts `arguments/params/parameters`); forwards to `tools.call_tool(name, args)`. `call_tool` uses `ToolBank.get_tool` to find definition, executes its `impl` (wrappers mostly calling `_call_bridge`), wraps responses via `ok_response`/`error_response`. No JSON-schema validation is enforced at runtime.
- Bridge execution path: `_call_bridge` -> `mcp_core.bridge_client.bridge_request` -> HTTP POST to Blender bridge `/exec`. Bridge handler enqueues execution onto Blender main thread via `task_queue` timer; waits up to `_WAIT_TIMEOUT` (default 90s, env `ATHENA_BRIDGE_TIMEOUT`/`ATHENA_BLENDER_BRIDGE_TIMEOUT`). Executor functions live in `blender_bridge/executor.py`.
- Timeouts: MCP-to-bridge client default `_DEFAULT_TIMEOUT` = `_get_bridge_timeout(default=60)` (env override) in `mcp_core/bridge_client.py`; bridge server wait timeout `_WAIT_TIMEOUT` default 90s (same env vars) in `blender_bridge/provider_http.py`; viewport screenshot also has per-call timeout guard in `executor.viewport_screenshot_complete` (30s).
- Error format returned to clients: MCP transports use `mcp_core.types.error_response/ok_response` shape `{"ok": False, "error": {"message", "code", ...}}`; bridge uses same shape via `blender_bridge.responses`. `bridge_client` maps non-200 or connection issues to `{"ok": False, "error": {"code": "...", "message": "...", "details": ...}}`; `transport_http` unwraps nested bridge responses and surfaces `bridge_tool_error` codes.

## 3) Problems & risks (ranked)
- P0 — No cancellation on bridge timeouts can leave Blender running a stuck tool: `blender_bridge/provider_http.py:362-408` enqueues work on the main thread and waits `done.wait(_WAIT_TIMEOUT)`. If an executor function hangs beyond the timeout (or blocks the queue), MCP returns a timeout/bridge error but the job keeps running in Blender (no cancellation or queue drain), risking ghost operations or UI lockups. Client-side default timeout is shorter (60s) than bridge wait (90s), increasing the chance of mid-flight abandonment.
- P1 — MCP exposes tools that the bridge does not implement: `tools/registry.py` defines ToolDefinitions (e.g., `blender-primitive-cone`, `blender-primitive-torus`, many mesh/modifier ops), but `blender_bridge/provider_http._build_dynamic_registry` only exposes functions that exist in `blender_bridge/executor.py`. `validate_tool_naming.py` currently reports 29 missing bridge registrations, so calls to those MCP tools will return `unknown_tool` at the bridge. This is a contract drift between MCP specs and the bridge runtime.
- P2 — No runtime schema validation for tool args on the MCP side: `transport_http.do_POST` and `call_tool` only check type is dict; they do not validate against `specs_v2`/`vision_specs`. Bad payloads reach the bridge and rely on executor-side checks, reducing early feedback and test coverage for argument contracts.

## 4) Fix plan without coding
- 1) Align timeout behavior: choose a single timeout budget for MCP client and bridge wait (likely the longer 90s), document it, and ensure client waits at least as long as the bridge to avoid orphaned executions; add cancellation/cleanup for overrun tasks if possible. (Config/logic change, no new deps.)
- 2) Close the MCP/bridge contract gap: either implement the 29 missing executor functions or temporarily remove/feature-flag the corresponding ToolDefinitions until the bridge supports them; rerun `validate_tool_naming.py` to confirm zero missing entries.
- 3) Add lightweight request validation: enforce JSON-schema (or at least required fields/ranges) for tool args before dispatching to the bridge, reusing existing `specs_v2`/`vision_specs` definitions; return clear MCP-side errors to callers.
